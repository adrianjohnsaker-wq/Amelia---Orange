# Live synthetic source in Amelia

The application field panel now has an **opt-in** live synthetic source. When connected, each field step measures the current body, updates the same engineered adaptive source used by the registered experiment, and sends its response through the shared Governor and Numogram. The source does not run while the field is paused. Its two profiles are intentionally programmed; this control does not assert an external or conscious entity.

The source's enabled state, address and internal history are stored inside the existing field checkpoint alongside Amelia's runtime and lineage. Every source offer adds its body digest, current pointer vector, regional means, source step and source-state digest to the Governor decision recorded in PFM. The PFM event also records the response, whether it was attended/deferred/refused, and the resulting Numogram transition. The field and PFM then use the application's existing local and authenticated Supabase persistence. A previously deferred observation may still be handled by the Governor after the user stops new source offers.

Open **Live Morphogenetic Lab**, choose **Connect synthetic source**, and step or run the field. The source remains off until the user connects it. Navigating to another panel preserves the field and the enabled source; its source state is restored with the field on a new app session. **Stop new source offers** pauses that source while retaining its state. The existing explicit field reinitialization or a change of field configuration creates a new field and source session.

This interactive control is for live exploration. It does not automatically execute the registered four-arm, mirrored-body and withdrawal protocol: that controlled study is the isolated driver in `run.ts`. Its outputs and the original preregistered code are preserved at the commit cited in `RESULTS.md`. Moving the identical source implementation into the application and adding optional richer PFM context did not alter the historical study: an additional deterministic regression replay matched all 2,240 original rows and 64 original checkpoints.

## Tablet build

The research-branch APK is built with the separate Android application ID `org.amelia.orange.research` and label **Amelia Orange Research**. It can coexist with the existing `org.amelia.orange` app; it is not a signed in-place upgrade of that app. The workflow records the package name, build commit, APK hash and signing certificate. Preserve the existing app and its data. On first authenticated sync, the research app copies the main account records into a separate account-protected `amelia_research_records` table; later research saves use that table and leave the main checkpoint unchanged. Both tables use account-based row-level security. Two research installations using the same account can still compete because there is no cross-device write lease. Older app versions access only the main memory table. A real tablet installation, actual sign-in and live source run still need device verification; browser tests used an isolated mock account.

## Verification

Run `node --import tsx --test experiments/live-pointer-baseline/*.test.ts experiments/live-amelia/*.test.ts`. `live_source_browser.mjs` tests the actual UI, including local restart, continued stepping while its panel is hidden, and pausing across another restart. `experiments/live-amelia/browser_session.mjs` tests source-state transfer to a separate browser profile and conflict protection using a local mock of Supabase. `research_namespace_browser.mjs` tests the separate-table build, including interrupted bootstrap, account transfer and protection of the original main records. These browser tests require Playwright and Chromium as described in the earlier live-amelia README; they do not reach the real Supabase project.

The additive table definition is in `research_table_schema.sql`. On the configured Supabase project the table was created empty, and a rolled-back access test verified that the owner can read and update a row while a different authenticated account cannot read, update, or insert a row for that owner. The existing main checkpoint was checked again after the migration and was unchanged. Real-device authentication and cloud transfer have not yet been exercised.
